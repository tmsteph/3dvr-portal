Any device can be anything.

A distributed live-production system where devices advertise capabilities, shows assign roles, and cues coordinate presentation, audio, lighting, video, control, and automation across the network.

Fundamental model

Hardware contributes. The show decides.

A Mac, Linux workstation, Windows PC, Raspberry Pi, RISC-V board, phone, tablet, server, or embedded controller is simply a node. It tells the network what it can do. Those capabilities can be assigned one or many roles, and those roles can move while the show is running.

Cue engine

One GO can move the whole room.

A cue asks for actions. It does not need to know which physical machine performs each one. The network resolves the capable node or assigned role.

GO 42 ├─ Presentation → next slide ├─ Lighting → recall “Keynote” ├─ Lighting → fade house lights to 20% over 3 sec ├─ Audio → fade walk-in music ├─ Mixer → unmute presenter ├─ Video → roll keynote opener └─ OSC → /show/keynote/start

Discovery

The room can assemble itself.

A node discovers the network, authenticates, advertises capabilities, discovers the show, receives roles and resources, synchronizes state, and becomes ready.

Discover network → Authenticate → Advertise capabilities → Discover show → Receive roles/resources → Synchronize state → Ready

A future operator could simply hear: “I found three displays, two audio outputs, one DMX interface, two cameras, and five control surfaces. How should we use them?”

Presentation

Slides are sources

PPTX, PDF, images, HTML, and native scenes can all feed the presentation role. PowerPoint is an input format, not the architecture.

Video

Anything that can render

Local files, network streams, cameras, generated graphics, and future 3D scenes can become video resources.

Audio

Anything that can sound

Local playback, USB interfaces, network audio, multichannel stems, and external mixer control can share the same cue system.

Distributed state + failover

A failed device should not have to stop the show.

Shows, scenes, cues, nodes, roles, displays, fixtures, channels, audio buses, media, and resources all receive addressable identities. Nodes synchronize the state they need, while roles can migrate when hardware disappears.

Takeover

Presentation Node A fails

Presentation Node B can assume presentation-output automatically or after operator approval.

Policies

Choose the right resilience

Automatic takeover, operator-approved takeover, mirrored playback, hot standby, and degraded-mode operation can all coexist.

Control surfaces

Different views into the same show.

Any node capable of displaying an interface can become a controller. The interface changes with the role; the underlying show does not.

Design law

Never bind functionality unnecessarily to a physical device.

Prefer

“Find a node capable of rendering this presentation.”

Avoid

“Send this to Laptop 2.”

Prefer

“Route this audio to the stage playback role.”

Avoid

“Play this through USB interface 3 on computer A.”

Physical hardware remains directly addressable when necessary. The higher-level show operates through capabilities and roles.

Vision

A distributed operating system for live production.

Instead of separate “lighting computers,” “audio computers,” “presentation computers,” and “control tablets,” Open Show Control sees a network of cooperating nodes. Every connected device contributes whatever capabilities it has. Every capability can become part of the show.

Any device. Any role. One show.
