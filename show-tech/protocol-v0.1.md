# 3DVR Show Node Protocol 0.1

Status: experimental, implementation-backed.

## Design rules

1. A node advertises capabilities; the Core never assumes every node has the same hardware.
2. Control/state messages stay small and separate from audio/video media transport.
3. Time-sensitive actions may be delivered early and executed locally by the node.
4. Actions have stable IDs so future implementations can make retries idempotent.
5. Hardware-specific details belong behind adapters, not in show files.

## Discovery

A controller broadcasts the UTF-8 payload below over UDP port `47770`:

```text
3DVR_SHOW_DISCOVER_V1
```

A node replies to the sender with JSON:

```json
{
  "id": "stage-left-a1b2c3",
  "name": "stage-left",
  "platform": "linux",
  "arch": "riscv64",
  "protocol": "3dvr-show-node/0.1",
  "httpPort": 47771
}
```

Discovery is only a locator. It does not authorize control.

## HTTP endpoints

### `GET /v1/health`

Liveness and node ID.

### `GET /v1/capabilities`

Returns node identity plus capability/action declarations.

### `GET /v1/state`

Returns current adapter state represented by this prototype.

### `GET /v1/events`

Server-Sent Events stream for state/action results.

### `POST /v1/actions`

Requires:

```text
Authorization: Bearer <SHOW_NODE_TOKEN>
```

Action envelope:

```json
{
  "id": "cue-42-screen-1",
  "type": "display.text",
  "executeAt": 1788216000000,
  "payload": {
    "text": "GO"
  }
}
```

Fields:

- `id`: caller-supplied stable action ID; generated by the prototype if omitted.
- `type`: capability-specific action name.
- `executeAt`: optional Unix epoch milliseconds; immediate when omitted.
- `payload`: action-specific parameters.

The prototype accepts actions up to 24 hours ahead. A production scheduler should persist queued actions and use a synchronized monotonic-clock strategy rather than relying only on `setTimeout`.

## Capability envelope

```json
{
  "protocol": "3dvr-show-node/0.1",
  "node": {
    "id": "stage-left-a1b2c3",
    "name": "stage-left",
    "platform": "linux",
    "arch": "riscv64"
  },
  "endpoints": {
    "httpPort": 47771,
    "outputPath": "/output"
  },
  "capabilities": [
    {
      "id": "display.browser",
      "kind": "video.output",
      "actions": ["display.color", "display.text"]
    }
  ]
}
```

## Future protocol work

Before calling the protocol stable, add:

- pairing and node identity keys rather than shared bearer tokens;
- idempotent action journal and replay protection;
- clock offset/quality reporting and synchronization policy;
- persisted cue queues and reboot recovery;
- asset manifests, hashes, preload status, and cache management;
- logical port/deployment patch schema;
- richer result/error envelopes;
- adapter health and hot-plug events;
- TLS/encrypted transport outside trusted lab networks;
- multicast/mDNS discovery option where appropriate.
