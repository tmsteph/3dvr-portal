Swarm execution

The Digital Twin can operate as a swarm of small, specialized AI workers coordinated through the existing durable queue. Instead of one giant agent doing everything, a coordinator can delegate work to Scouts, Booking Agents, Sales workers, Builders, Ops workers, Researchers, Archivists, and Treasurer/Supervisor functions.

Workers get only the capabilities needed for the task, run in parallel when resources are healthy, and stay queued when CPU, RAM, browser lanes, or API limits are tight. Routine work should use the cheapest adequate model or deterministic code; stronger models are reserved for work that actually needs them.

Many minds, one owner. The swarm may plan and execute in parallel, but the person's goals, identity, data, permissions, and durable memory remain anchored to the Digital Twin.

Portable by design

If the cloud server disappears or becomes unaffordable, the person should be able to restore the same twin on a normal Linux laptop and continue. State, policies, opportunities, contacts, task history, connector configuration, and private encrypted data must be exportable. Secrets stay behind logical aliases so they can be reconnected without being baked into backups.

The target recovery experience is deliberately simple: clone → install → restore → doctor → start.

Built for more than Thomas

Thomas is the first deployment, not a hard-coded product assumption. Every durable record should belong to a stable twin/owner identity, with isolated queues, browser workspaces, connector configuration, policies, audit history, and learning memory.

Current foundation

This is not a blank-slate concept. The Portal already has durable SQLite agent execution, Workboard runtime state, Freelancer scheduling and booking policy, isolated persistent browser workspaces, OVH resource lanes, a roaming device mesh, Opportunity Inbox / Money Printer intelligence, and verified workforce access paths for IATSE, UKG/UltiPro, Encore SharePoint, and Lighthouse.

Next build
